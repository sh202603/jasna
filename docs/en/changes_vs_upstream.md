## 1. Scope of this public build

- **Supporter models are inert.** `unet-4x`, SD 1.5 image restoration and the activation flow need the private `jasna/protection` submodule, which this public fork does not have. The upstream code rides along and does nothing. For those models use the official upstream release.
- **LTX restores video here only with a model of your own.** The release LTX weights ship encrypted (`.enc`) and only the official release decrypts them, so with those weights `--restoration-model-name ltx` / `ltx-4step` / `ltx-8step` / `ltx-undistilled` and the GUI's LTX modes do not work, and `--ltx-trial` runs with random weights and only measures speed. The inference path itself is public and loads plaintext safetensors: [ltx_lora_training.md](ltx_lora_training.md) builds a model for it from a public LTX-2.3 checkpoint and an IC-LoRA trained on mosaic/clean pairs ([3.8](#38-training-your-own-ltx-model-scriptsltx_lora_training)). LTX's public parts (the mosaic scan and the compositor) are what [`--ltx-crop-vsr`](#36-sharpening-ltx-outputs---ltx-crop-vsr) reuses to sharpen a video the official release restored.
- **Everything else works**: detection, BasicVSR++ restoration, RTX Super Res and TVAI secondaries, the Segment Editor, VR180, streaming, post-export actions, plus the modi features below.
- **Run from source.** This fork is set up from the build guides ([Linux](building_linux.md), [Windows](building_windows.md)); an experimental Windows bundle can be built with `scripts/build_nuitka.py` ([frozen_build.md](frozen_build.md)).

## 3. Restoration models

### 3.1 SeedVR2 + LoRA primary restoration

`--restoration-model-name seedvr2` replaces BasicVSR++ with SeedVR2 3B (one-step SR diffusion) plus a custom LoRA trained to remove mosaic as cell-averaging degradation (rank 16, ~90 MB, [sh202603/lada-seedvr2-lora](https://huggingface.co/sh202603/lada-seedvr2-lora), AGPL-3.0). The detected 256 px crops go through the diffusion forward at scale 1; detection, crop extraction, blend and encode are unchanged, and the default `basicvsrpp` path stays bit-identical. Positioning: strongest on low-resolution, heavily degraded sources, where the diffusion prior rebuilds detail BasicVSR++ only smooths; it adds plausible detail rather than recovering signal, so it is chosen per source and `basicvsrpp` stays the default. Ported from this fork's lada-ex implementation.

- **Process model.** A resident worker in the user-supplied [ComfyUI-SeedVR2_VideoUpscaler](https://github.com/numz/ComfyUI-SeedVR2_VideoUpscaler) venv (`jasna/restorer/seedvr2_lora_worker.py`, no jasna imports) exchanges one clip at a time as JSON header + raw uint8 BGR over stdin/stdout; it is respawned and the clip retried once on death, with no pass-through fallback (a skipped clip would leave mosaic in the output). Inside: LoRA injection via peft, 33-frame / stride-24 sliding windows cross-faded in a GPU-resident float32 accumulator, one final quantization, per-clip LAB color transfer referenced to the mosaic crops, and a VRAM-gated per-clip `empty_cache` (`--seedvr2-empty-cache`, `auto` releases only below 20 GiB total VRAM).
- **jasna-side adaptations.** Zero padding instead of reflect padding for this restorer (`pad_mode`, the LoRA's training distribution); the wire stays BGR with the RGB flip in the parent adapter; and two blend-side reverts gated by restorer attributes so BasicVSR++ stays bit-identical: `_revert_valid_edges` (the VAE/DiT bleeds the zero padding 2–3 px into the crop, which composited as a dark line along bbox edges) and `_revert_outside_mask` (a one-step diffusion resynthesizes the whole crop, so the blend falloff annulus carried drifted low frequencies; everything outside the detection mask's trust zone is reverted to the input with the blend mask's own falloff as the ramp, plus a crop-border ramp for mosaics that fill the crop).
- **Acceleration** (`--seedvr2-accel`, off by default): the fused VAE path (`fused_vae`, comfy-kitchen kernels) and the FP8 DiT (`fp8_dit`, LoRA merged into the base weights first), both provided by the `modi` branch of the fork [sh202603/ComfyUI-SeedVR2_VideoUpscaler](https://github.com/sh202603/ComfyUI-SeedVR2_VideoUpscaler). The worker drops the parts it cannot run and says why in the ready handshake (upstream checkout: both dropped, output bit-identical to off). Measured whole-run wall clock on 2-minute clips: Linux RTX 5080 1.68–1.77x faster (480p 117 → 70 s, 1080p 220 → 126 s, 4K 272 → 154 s), Windows RTX 5080 1.45–1.57x; GPU-wide VRAM peak 3.1–3.7 GiB lower; output 46–50 dB PSNR against off and judged visually equivalent.
- **Flags.** `--seedvr2-repo` (required), `--seedvr2-python`, `--seedvr2-lora`, `--seedvr2-window` / `--seedvr2-overlap` (33 / 9), `--seedvr2-color-fix {none,lab,wavelet}`, `--seedvr2-empty-cache {auto,always,never}`, `--seedvr2-accel`, and the base-weight overrides `--seedvr2-model-dir`, `--seedvr2-dit`, `--seedvr2-lora-rank`.
- **Constraints.** VR modes, `--frame-generation`, `flashvsr-inline` and `swiftvr-inline` are rejected at startup (two resident workers exceed 16 GB); TVAI and `--stream` warn. The offline `flashvsr` / `swiftvr` modes compose with it (their phases never co-reside), which is the maximum-quality stack. BasicVSR++ engine compilation is skipped when seedvr2 is selected. Since the v0.11.1 base `seedvr2` is one entry of upstream's restoration-model choice (`CLI_RESTORATION_MODELS`, `provide_restoration_models`), so it also appears wherever upstream lists the model.
- **Status.** Unit tests `tests/test_seedvr2_lora.py` + the validation matrix in `test_main.py`. Verified end to end on Linux and Windows (frame count = input, clean worker shutdown; 480p all-mosaic peaks at 12.6 GB whole-pipeline). The A/B comparison ([6.1](#61-ab-model-comparison-segment-editor)) can select seedvr2 as a side.

### 3.2 FlashVSR secondary restoration

A secondary restorer that upscales each 256 px primary crop with the one-step diffusion VSR model [FlashVSR](https://github.com/OpenImagingLab/FlashVSR) and re-blends it, recovering texture BasicVSR++ leaves blurry on large mosaics, close-ups and 4K. The crop is processed at 1024 px (4x, model-native) or 512 px (`--flashvsr-scale 2`); the output resolution never changes. You supply a checkout, the weights and a dedicated venv (`--flashvsr-repo`); the fork [`sh202603/FlashVSR_plus`](https://github.com/sh202603/FlashVSR_plus) is recommended (it carries the tiny-long fix and the acceleration; `uv sync` installs its dependencies). The venv's base Python must ship the dev headers (Triton JIT at runtime). Two modes:

- **`flashvsr` (offline 3-phase).** `dump → FlashVSR → reblend` as three sequential subprocesses, each releasing its VRAM at exit, so the ~12–16 GB tiny-mode peak never overlaps the ~9 GB primary. Keeps an intermediate bundle on disk (hundreds of GB on long mosaic-heavy videos; a quarter at scale 2) with staged resume via `--flashvsr-bundle-dir`. Works on 12 GB-class GPUs; encodes twice. `jasna/restorer/flashvsr_offline.py` + `flashvsr_phase2_driver.py`, subprocess dispatch via `--flashvsr-phase` in `jasna/__main__.py`.
- **`flashvsr-inline` (single pass).** FlashVSR's **tiny-long** pipeline (constant ~11.9 GB regardless of clip length) co-resides with the primary, which [`--fp8-recon`](#52-cudnn-fp8-upsample-backend---fp8-recon) (auto-enabled) shrinks to ~1.6 GB. A synchronous `SecondaryRestorer` spawns a resident worker in the FlashVSR venv and exchanges crops over a length-prefixed uint8 BGR protocol; the worker file is kept verbatim-identical with lada-ex's `flashvsr_worker.py` (the RGB flip lives in the jasna adapter). `--flashvsr-tiles {1..4}` runs the DiT per horizontal strip as a VRAM lever. Needs a 16 GB card. `jasna/restorer/flashvsr_inline_secondary_restorer.py` + `flashvsr_inline_worker.py`.

Shared behaviour (both modes unless noted):

- **Color correction, always on**: each output crop is matched to the bicubic-upscaled primary output by wavelet reconstruction (high frequencies from FlashVSR, low frequencies from the reference), removing the tone step between the blended region and its surroundings (median |Δmean| in the changed pixels 1.7 → 0.25). `JASNA_FLASHVSR_COLOR_FIX=adain|wavelet|none` is a verification-only override.
- **Clip length**: inline follows `--max-clip-size` (default 90); the offline `--flashvsr-max-clip-frames` defaults to 90. The former 32-frame cap roughly doubled FlashVSR time through overlap re-processing.
- **The worker verifies every clip**: tiny-long swallows exceptions in its chunk loop, so a mid-clip OOM used to return a truncated clip padded with its last frame (ghosting). The worker now checks the return value and frame count, retries once after releasing the cache, and fails the clip loudly. Consequence: scale 4 without tiles is not usable on 16 GB; use `--flashvsr-tiles 2`.
- **`--flashvsr-accel`** (off): the fork's FP8 projector convolutions, FP8 DiT linears and fused kernels, about 1.4x faster with a 1.4 GiB lower peak; each part falls back automatically below RTX 40, with fp16, `-v 10` or an upstream checkout, and an all-fallback run is bit-identical to off. The worker reports active parts in the ready handshake and runtime demotions in the clip response.
- **`--flashvsr-lora`** (inline only): applies the published `lada_flashvsr_secondary_lora_v1.pt` to the DiT as bf16 adapters, toning down FlashVSR's mid-frequency over-sharpening (about −30 % in the 4–8 px band) and excess grain; combines with `--flashvsr-accel`. The offline mode rejects it (its main use, a SeedVR2 primary, loses most of FlashVSR's added grain).
- **tiny-long patch**: inline needs the multi-chunk fix (two per-chunk cache clears disabled). The fork has it; for an upstream checkout apply [`patches/flashvsr_plus_tinylong_multichunk_fix.patch`](../../patches/flashvsr_plus_tinylong_multichunk_fix.patch). The restorer checks for it at startup and stops with an explicit error otherwise.
- **Flags**: `--flashvsr-repo` (required), `--flashvsr-python`, `--flashvsr-model-dir`, `--flashvsr-version` / `--flashvsr-dtype`, `--flashvsr-scale {2,4}`, `--flashvsr-tiles`, `--flashvsr-accel`, `--flashvsr-lora`, and the offline knobs `--flashvsr-max-clip-frames`, `--flashvsr-unload-dit`, `--flashvsr-tiled-vae`, `--flashvsr-bundle-dir`, `--flashvsr-keep-bundle`.
- **Constraints**: file output only (no `--stream`, no image input) and no `--frame-generation` (run it as a separate pass). Offline additionally rejects `--retarget-high-fps`, `--segments` and VR. Inline is exclusive with the SeedVR2 primary; offline composes with it. Inline runs at FlashVSR's ~15 crop-fps on mosaic-heavy stretches.
- **Status**: unit tests `tests/test_flashvsr_{offline,inline}.py` + `test_main.py`. Verified end to end on Linux and Windows at 480p and 1080p in both modes and both scales (frame count = input, only the mosaic regions change). Headline numbers (Linux, 480p, 4930 frames, clip 90): inline scale 2 / tiles 1 in 113 s at a 10.1 GB whole-GPU peak, scale 4 / tiles 2 in 491 s at 13.7 GB; offline scale 2 in 194 s / 7.8 GB. On Windows 16 GB, tiles 2 is the recommended 1080p setting. Measurements and the color-correction gate: [flashvsr.md](flashvsr.md).

### 3.3 SwiftVR secondary restoration

`--secondary-restoration swiftvr-inline` (inline) and `swiftvr` (offline 3-phase) fill the same role as FlashVSR with [SwiftVR](https://github.com/H-oliday/SwiftVR) (one-step streaming diffusion VSR on a Wan2.2-TI2V-5B backbone, Apache-2.0); the fork [`sh202603/SwiftVR`](https://github.com/sh202603/SwiftVR), branch `modi`, is required (it adds `SwiftVRPipeline.restore_clip()`, an in-memory clip API that preserves the frame count). Crops go to 1024 px (4x) or 512 px (`--swiftvr-scale 2`). You supply the checkout, the ~20 GB checkpoint and a `uv sync` venv (`--swiftvr-repo`). On the same machine SwiftVR inline is about 2.4x (scale 2) to 3.3x (scale 4) faster than FlashVSR inline at 1080p.

- **Inline** uses the same synchronous `SecondaryRestorer` and BGR wire as `flashvsr-inline` with a worker in the SwiftVR venv (`jasna/restorer/swiftvr_inline_worker.py`). SwiftVR restores in fixed chunks (28 frames, then 24), so VRAM is independent of the clip length and there is no clip cap; short clips are padded inside `restore_clip()`.
- **Offline 3-phase (`swiftvr`)** shares FlashVSR's orchestrator (`flashvsr_offline.py`) through an engine record (`OfflineEngine`): Phase 1, Phase 3, the bundle (version 2, carrying `view_placements`), the disk checks and the `--flashvsr-phase` hook are the same; Phase 2 runs `swiftvr_phase2_driver.py` under the SwiftVR venv and reuses the inline worker's functions. bf16 is the regular path there (the SwiftVR phase has the GPU to itself), so it is the mode for 12 GB-class GPUs, GPUs without FP8 and the SeedVR2 primary. A lossless encode of an offline run is bit-identical to the inline run when `--fp8-recon` is passed to Phase 1.
- **Acceleration on by default (`--swiftvr-accel`, `--no-swiftvr-accel` to disable)**: the fork's FP8 DiT and torch.compile. The worker checks the GPU generation (sm89+) and that Triton can build a kernel before loading, drops what fails and reports it in the handshake. Without FP8 the DiT runs in bf16 (~12 GiB), which does not co-reside with the primary on 16 GB: jasna warns and continues, and the run fails on OOM if memory runs out.
- **Color correction, always on** (wavelet against the bicubic-upscaled primary), applied on the GPU per frame; the primitives are loaded by path from the FlashVSR worker so that file stays verbatim-identical with lada-ex's. `JASNA_SWIFTVR_COLOR_FIX` is the verification-only override.
- **Crop view smoothing (`--swiftvr-view-window`, default 15, `0` disables)**: the main cause of the scale 2 flicker was the crop framing moving from frame to frame (the crops follow the detection box, and SwiftVR redraws its detail on sub-pixel shifts). At the end of the primary stage each frame's 256 grid is resampled into a view placed at the moving average of the placements over N frames; the blend resamples straight from the view into the frame. Crop-level flow-warping error ratio at scale 2: 4.99 → 2.57 (scale 4: 2.16). The primary restoration, the mask, the worker and the wire are unchanged, and the disabled case and the other secondaries stay bit-identical. `jasna/tracking/crop_view.py`, `restoration_pipeline.py`, `blend_buffer.py`, `pipeline_items.py`. The cause and the fix come from a report by [mioh-labs](https://github.com/mioh-labs/mioh).
- **Flags**: `--swiftvr-repo` (required), `--swiftvr-python`, `--swiftvr-model-dir`, `--swiftvr-scale {2,4}`, `--swiftvr-view-window`, `--swiftvr-accel`, and the offline-only `--swiftvr-bundle-dir` / `--swiftvr-keep-bundle`. No dtype, version, tiles, LoRA or max-clip-frames flag.
- **Constraints**: the same startup checks as FlashVSR's modes (inline: fp8-recon auto-enabled, `--frame-generation` rejected, exclusive with the SeedVR2 primary; offline: `--stream`, VR, `--segments`, `--frame-generation`, `--retarget-high-fps` and folder/image input rejected, SeedVR2 primary allowed). Not exposed in the GUI.
- **Status**: `tests/test_swiftvr_inline.py`, `tests/test_swiftvr_offline.py`, `test_main.py`. Verified end to end on Linux and Windows in both modes, both scales, at 480p and 1080p; visual A/B (the user's) finds scale 4 on par with FlashVSR in texture and, with view smoothing, scale 2 on par with scale 4 in temporal steadiness. Whole-GPU peaks (Linux inline): 12.6 GB at scale 4 FP8, 10.3 GB at scale 2. Full measurements, Windows notes and the "What determines temporal stability" investigation: [swiftvr.md](swiftvr.md).

### 3.4 SwiftVR distill secondary restoration

`--secondary-restoration swiftvr-distill` runs a small convolutional student distilled from SwiftVR's outputs (`TinyROIEnhancer`, 24 channels, 12 residual blocks, ~131k parameters, checkpoint `roi-distill-pilot-v1`) in place of SwiftVR: five 256 px primary crops in, the centre frame out at 512 px (2x), re-blended like `--swiftvr-scale 2`. PyTorch FP32 inside the jasna process, with no checkout, venv or worker. The weights were trained and published by the author of [mioh](https://github.com/mioh-labs/mioh) at [`okatti/swiftvr-distill`](https://huggingface.co/okatti/swiftvr-distill) (AGPL-3.0); they are not bundled: put `swiftvr-distill.pt` in `model_weights/` (or pass `--swiftvr-distill-model`).

- **Restorer**: `jasna/restorer/swiftvr_distill_secondary_restorer.py` (batches of 4 centre frames, clip edges repeated for the five-frame window); the model definition in `swiftvr_distill_model.py` follows the published README (3x3 conv 15→24 + ReLU, 12 blocks `x + 0.1 * conv(relu(conv(x)))`, 3x3 conv 24→12 + PixelShuffle(2), output = bilinear 2x of the centre frame plus that detail). The loader accepts only a validated dict read with `weights_only=True`.
- **Flags**: `--swiftvr-distill-model`, `--swiftvr-distill-view-window` (default 15, the crop view smoothing of 3.3 reused), `--swiftvr-distill-strength` (default 0.75, 0–2, scales what the model adds to the bilinear upscale), `--swiftvr-distill-stabilize` (default 0, experimental; on the test clip it only traded detail for flicker like a lower strength).
- **No coupling**: fp8-recon is not auto-enabled, `--frame-generation` is not forced off, the SeedVR2 primary is not excluded, and there is no color correction. Not exposed in the GUI. `--stream` and `--segments` are unverified.
- **Status**: `tests/test_swiftvr_distill.py` + `test_main.py`. Verified on Windows (2026-10-05) and Linux (2026-10-08): on 1080p footage the defaults give a flicker increase of +8.6 % at texture 122 % (relative to no secondary) against +10.9 % / 130 % for `swiftvr-inline` at scale 2; the secondary stage takes about 1/7 of SwiftVR's time (1080p, 4203 frames: 5.8 s vs 38.9 s) and adds at most 0.4 GB of VRAM against ~5.5 GB. An 8K SBS VR clip completes. The user's visual check found the flicker unobtrusive and the texture acceptable. Details: [swiftvr.md](swiftvr.md#swiftvr-distill---secondary-restoration-swiftvr-distill).

### 3.5 RTX Super Res extras

Two opt-in knobs on the `rtx-super-res` secondary restorer, exposed by `nvidia-vfx` 0.2.0.0; the defaults (strength 1.0, standard models) reproduce the previous behaviour.

- **`--rtx-strength <0.0-1.0>`**: the SDK's `strength`, applied to every RTX pass (upscale, denoise, deblur); lower values blend toward the unprocessed picture. Forwarded only when it differs from 1.0, so the default still constructs on a venv with 0.1.0.1.
- **`--rtx-highbitrate`**: the `HIGHBITRATE_{LOW..ULTRA}` upscale family instead of `LOW..ULTRA` at the chosen `--rtx-quality`. Those models skip compression-artifact suppression; BasicVSR++ output has no compression noise, so the hypothesis is that they keep more detail. Denoise/deblur passes are unaffected.
- Plumbing: `SessionConfig.rtx_strength` / `rtx_highbitrate`, `RtxSuperresSecondaryRestorer(strength=, highbitrate=)`, a slider and a switch in the GUI's RTX Super Res panel (part of the video-session key), `tests/test_rtx_superres_restorer.py`.
- **Status**: both change the output measurably on the 1080p test clip (PSNR against the default: `--rtx-highbitrate` 47.8 dB, `--rtx-strength 0.5` 48.7 dB) and a visual check (2026-10-03) found no artifacts in either; whether they look *better* is content-dependent, so both stay opt-in.

### 3.6 Sharpening LTX outputs (`--ltx-crop-vsr`)

This build cannot run LTX, but LTX's scan and compositor are public. `--ltx-crop-vsr swiftvr|swiftvr-distill|rtx-super-res` takes a video the official release restored with LTX (`--input`) and the video it was restored from (`--ltx-crop-vsr-source`), reruns LTX's scan on the source, crops the LTX output with the same cameras, upscales every 121-frame window 2x with SwiftVR (the full model through the inline worker at scale 2, or the distill student in-process) or with RTX Super Res (nvvfx, frame by frame, its deblur pass on by default since that is the pass that sharpens) and composites it back with LTX's own `composite_frame`. The output keeps the LTX output's resolution, frame count and timestamps. CLI only, one video at a time.

- **Module** `jasna/ltx/refine.py`: an alignment check (packet-level demux of both videos: frame counts, frame sizes and each frame's time from its stream start within half a frame), the scan (`scan_span` as one segment, `--ltx-large-canvas` taken as given, detector released afterwards), and `WindowRefiner`, the one-pass driver: canvases built from the LTX frames as they arrive, a window upscaled once complete, frames held in page-locked host buffers (at most 121) until every window covering them is done. The LTX output and the source decode in lockstep; the mean luma difference inside the track polygon tells a window LTX restored from one it left alone (threshold 3/255), and the latter is skipped with a warning so a track found only by this build's detector numerics is never sharpened with its mosaic.
- **Wiring**: `SessionConfig.ltx_crop_vsr` / `ltx_crop_vsr_source`; `build_restoration_session` compiles only the detector engine and loads no primary; `build_ltx_crop_vsr_restorer` builds the restorer after the scan (scale 2, view smoothing off; `RtxSuperresSecondaryRestorer(input_size=None)` loads one set of nvvfx passes per canvas side, 512 and 768 px, since an effect is bound to its output size); `Pipeline.run` branches to `_run_ltx_refine`. The BasicVSR++ weights are not required.
- **Refused**: the primary options, everything that changes the frame sequence or the whole picture (`--segments`, `--ltx-auto-split`, `--stream`, `--retarget-high-fps`, `--fmp4`, `--frame-generation`, VR, image and folder input, `--lut`, `--sharpen`), `--swiftvr-scale 4`, `--rtx-scale 4` with the `rtx-super-res` backend, the view-window options, and `--ltx-large-canvas` together with `--swiftvr-distill-stabilize`.
- **Status** (Linux, 2026-10-16): on two 30 s probe clips (720x480 and 1080p, LTX outputs of release v0.11.1) both backends complete with the release's plan (2 tracks, 11 windows) and the LTX output's frame count and timing (within 0.5 ms); texture 115–122 % at a flicker increase of +8–11 % against a re-encode; 23–28 s wall time with the distill student (2.5–2.8 GB of VRAM), 50–55 s with SwiftVR (9.8–10.8 GB, a 16 GB card). The user's visual check (five clips of 404p to 720p footage, SwiftVR at full strength) found the output as intended; on Windows (RTX 5060 Ti, 2026-10-16) both backends complete on the same clips with the same plan, frame count and timing (72–76 s with the distill student, 135–181 s with SwiftVR, at most 14.1 GB of VRAM for the whole GPU with SwiftVR). The 768 px canvas and small-mosaic footage are pending. **RTX Super Res backend** (Linux, 2026-10-22, the same clips): the x2 upscale alone is a near re-encode (texture 94–99 %), the deblur pass sharpens (medium: texture 120 % / 116 %, flicker +16 % / +7 %, the distill student's class) in 10–19 s with 1.2–2.1 GB of VRAM; the user's visual check passed (the 720x480 clip clearly sharper, the distill student softer but more natural in its detail; on the 1080p clip the backends hardly differ from the LTX output). Tests: `tests/test_ltx_refine.py`, `test_ltx_refine_cli.py`, `test_ltx_refine_gpu.py`. Details: [ltx_crop_vsr.md](ltx_crop_vsr.md).

### 3.7 Sharpening LTX windows in the run (`--secondary-restoration rtx-super-res`)

Upstream 0.12.1 added RTX Super Res for LTX windows (`b508fdab`, after this fork's proposal in issue #612): `--secondary-restoration rtx-super-res` with an LTX model upscales 2x the windows whose crop is larger than the model canvas, before compose enlarges them back, with `--rtx-deblur` as given (default `none`); the GUI offers it for LTX and auto split uses it too. This fork keeps its own policy on top of upstream's code (`jasna/ltx/super_res.py`, `LtxRender.super_res`):

- **Every window is upscaled when the deblur pass runs.** The canvas is shrunk back to its crop for most windows, so the 2x itself adds little; the deblur pass is what sharpens, and it sharpens the windows compose shrinks too. With an explicit `--rtx-deblur none` upstream's choice (only the enlarged windows) holds, since a 2x compose shrinks back changes nothing then.
- **Deblur `low` by default** in an LTX job with `rtx-super-res` (`LTX_SHARPEN_RTX_DEBLUR`; `--ltx-crop-vsr rtx-super-res` keeps `medium`). An explicit `--rtx-deblur` wins. The GUI's deblur setting is always explicit, so for an LTX job its `none` maps to `low`: in the GUI an LTX job cannot run super resolution without deblur (the CLI can, with `--rtx-deblur none`). The BasicVSR++ parts of an auto split use the same `--rtx-*` settings, deblur included, as in upstream.
- **The upscalers load before the first window decodes** (`LtxSuperRes.prepare`, one per canvas side the pass will upscale) and are freed after the compose pass (`release`): a single video's decode budget is the VRAM free at each decode, so an upscaler loading on first use would tile the first window apart from the rest. With auto split this repeats per segment.
- **Speed profile**: a run with super resolution keys its profile with `+rtx` on the budget name (compose is slower).
- **Checks**: an explicit `--rtx-scale 4` is refused for an LTX job without auto split (LTX windows always upscale 2x; with auto split the BasicVSR++ parts use the scale); nvvfx is checked before any model loads; `--rtx-strength` and `--rtx-highbitrate` ([3.5](#35-rtx-super-res-extras)) apply to the LTX windows too.

This build cannot run the encrypted release weights, so the option matters only with LTX weights it can load (plaintext safetensors, such as a model trained on the LTX-2.3 base, [3.8](#38-training-your-own-ltx-model-scriptsltx_lora_training)); `--ltx-crop-vsr` ([3.6](#36-sharpening-ltx-outputs---ltx-crop-vsr)) remains the way to sharpen an output of the official release.

- **Code**: `LtxSuperRes.sharpens` / `windows_to_upscale` / `prepare` / `release` and the `strength` / `highbitrate` arguments (`jasna/ltx/super_res.py`), `_SegmentComposer` and `compose_spans` / `_profile_key` (`jasna/ltx/restore.py`), `main._rtx_deblur()` / `_ltx_sharpens()`, the nvvfx check in `build_restoration_session`, `gui/video_session._rtx_deblur()`. The upscale call and its stream ordering are upstream's, the same as this fork's earlier `_sharpen_canvas`, so the output is unchanged. This fork's own implementation (`CanvasSharpener`, v0.11.3 base) was not replayed onto v0.12.1.
- **Status** (Linux, RTX 5080, 2026-10-24, v0.11.3 base, a self-trained LTX model on the two 30 s probe clips of 3.6): every variant completes with the plan (2 tracks, 9 windows) and frame count of the run without the sharpener; 0–6 % more wall time (2–4.5 s in the compose pass), no measurable VRAM change. Against the run without the sharpener, deblur `low` adds 18 % texture at +2–3 % flicker on both clips, which on the 720x480 clip is the amount the release model has over this one; `medium` adds 40 % there, well past that 22 % gap, and the user's visual check found it too sharp, hence the `low` default. On the 1080p clip the levels do not differ (+17–19 %), as under `--ltx-crop-vsr`. On the v0.12.1 base it is verified with the trial weights only. Tests: `tests/test_ltx_sharpen_cli.py`, `tests/test_ltx_sharpen_gpu.py` (trial weights, about 3 minutes), `tests/test_ltx_super_res_modi.py`.

### 3.8 Training your own LTX model (`scripts/ltx_lora_training/`)

This build cannot run the encrypted release weights, but jasna's LTX path loads plaintext safetensors from a model folder (`--restoration-model-path`, or `model_weights/ltx-restore/` by file name). The tools build such a model: a converter from ltx-core's LTX-2.3 bundle layout (Sulphur-2-base is the checkpoint used) to jasna's transformer file (tensor renaming and pruning, the fixed caption baked in as `prompt_context` from Gemma 3 plus the checkpoint's own projection and connector, a zero `keyframes_abs_pos_embedding`, LoRA fusion, ConvRot W8A8 or bf16), a bundle assembler with the public LTX-2.5 DiffVAE, Musubi Tuner (LTX-2 fork) helpers for an IC-LoRA on mosaic/clean 121-frame window pairs in jasna's own camera geometry (the pair dump lives in the author's lada-ex fork), and a window-level inference check. Full walkthrough: [ltx_lora_training.md](ltx_lora_training.md).

- **Code**: `scripts/ltx_lora_training/` only; the runtime is unchanged. A stock checkpoint converts and runs but reproduces its reference; the IC-LoRA is what adds restoration.
- **Status** (Linux, RTX 5080, 2026-10-30): the published converter reproduces the author's earlier model bit for bit; a rank 32 IC-LoRA trains at 11 to 12 s per step in 12.6 GB of VRAM and 32 GB of RAM; INT8 and bf16 models both run in jasna (bf16 through the torch.compile path with most blocks streamed from host RAM, about twice as slow per window). The model restores mosaics but comes out softer than the release model; the trained weights are not published. Windows and ARM64 are untested.

## 4. Frame generation

Upstream 0.12.2 added 2x frame generation with NVIDIA RTX Video Frame Generation (`--frame-generation 2x`, the Output tab, LTX jobs included). modi had the feature first (`--frame-gen`, the RIFE and RTX backends, 2x and 4x, the standalone `jasna-framegen`) and now keeps its policy on upstream's plumbing: `--frame-generation {none,2x,4x}`, `--frame-generation-backend {rtx,rife}`, `--frame-generation-rtx-mode`, `--frame-generation-model-path`. File output only.

- **Plumbing (upstream's)**: `Pipeline._frame_writer` wraps the pipeline's `FrameWriter`; the writer multiplies every PTS by the factor and the encoder divides the source time base by it (`frame_generation` is the multiplier, upstream's `True` still means 2x), so generated PTS stay whole on any time base; the last frame is repeated so `N` frames become `N * M` and the duration is kept; the bitrate ceiling scales with the factor. LTX jobs open the writer when compose starts (the generator loads after the denoiser is gone), so frame generation works on LTX too. `jasna/frame_generation.py` holds the writer (`FrameGenerationWriter`, a generator with `interpolate()` or upstream's midpoint callable) and `RtxFrameGeneration`, which runs modi's RTX generator on the default stream the way upstream's effect did.
- **Backends** (`--frame-generation-backend`, `jasna/framegen/`):
  - `rtx` (default, as upstream): NVIDIA RTX Video Frame Generation through nvvfx `VideoFrameGeneration` (`nvidia-vfx` 0.2.0.0+). No weights. Compute capability 8.9+ only (Ada / RTX 40 and newer; the SDK does not run on Turing/Ampere), with an error pointing at `rife`; Linux needs driver 570.190+/580.82+/590.44+. `--frame-generation-rtx-mode {low,medium,high}` (default `medium`; `high` is ~6x slower for a marginal gain), modi's addition to upstream's effect. Measured on RTX 5080 (v0.11 base): 1.53 ms per generated 1080p frame vs 10.1 ms for RIFE fp16 (2160p: 2.51 vs 48.3 ms), interpolation PSNR +0.7 dB (1080p) / +1.6 dB (2160p) over RIFE; visual A/B against RIFE passed.
  - `rife`: RIFE in PyTorch at full resolution on the blend-encode thread, fp16 by default (follows `--fp16`; an external TorchScript checkpoint with a baked-in float32 grid is detected and falls back to fp32). Loads a TorchScript checkpoint (recommended) or a state_dict into the vendored RIFE 4.6 `IFNet` (`jasna/models/rife/`). Weights via `--frame-generation-model-path` or `model_weights/rife.pth`; they are **not bundled** (Practical-RIFE weights carry non-commercial terms). `scripts/make_rife_torchscript.py` converts a Practical-RIFE checkout (verified with 4.25). Runs on every supported GPU, so it is what a Turing or Ampere card uses.
- **Standalone `jasna-framegen`** (`jasna/framegen_cli.py`, a second console script): applies **only** frame generation to an already-restored video, with no detection or restoration, reusing the same NVDEC/NVENC path and the shared writer (the generator is built once and borrowed across a folder batch); imports nothing from `jasna.pipeline` or `jasna.protection` (guarded by a test). Folder input/output with `--output-pattern`, videos only; `--backend`, `--rtx-mode`, `--model-path`.
- **GUI**: upstream's **Frame Generation** row in the **Output** tab offers 4x; the backend row (Advanced view), the RTX mode and RIFE weights rows (Expert view) are modi's. Without an RTX 40-series GPU only RIFE is offered, so frame generation stays available (upstream greys the feature out). Presets saved by earlier modi builds (`frame_gen`, `frame_gen_*`) migrate.
- **Constraints**: not for `--stream`; rejected with `--segments` and `--ltx-auto-split` (upstream's rules: the copied spans would no longer match the output rate), with the SeedVR2 primary, and with FlashVSR / SwiftVR in both modes (run frame generation as a separate pass). `swiftvr-distill` does not force it off.
- **Status**: `tests/test_frame_generation_modi.py`, `test_rife_frame_generator.py`, `test_rtx_frame_generator.py`, `test_framegen_cli_*.py` next to upstream's `test_frame_generation.py`. On the 10 s test clip (Linux, RTX 5080): 600 frames at 60 fps at 2x and 1200 at 120 fps at 4x with both backends on BasicVSR++, 600 at 2x with both backends on LTX (trial weights; LTX at 4x not run), and the duration stays 10 s. Details: [frame_generation.md](frame_generation.md).

## 5. Media and engine backends

### 5.1 torchcodec video backend

An experimental `torchcodec>=0.15.0` backend usable instead of native (upstream's PyAV NVDEC/NVENC with its VALI → PyAV-hw → PyAV-sw decode chain); optional dependency, off by default. `--video-backend {native,auto,torchcodec}` plus per-side `--video-decode-backend` / `--video-encode-backend {inherit,...}` (named apart from upstream's `JASNA_DECODE_BACKEND` / **Video Decoder**, which pick VALI or PyAV inside the native backend); the GUI has a **Video Backend** dropdown in the **Output** tab (Expert view). `--video-backend` sits one layer **above** upstream's `JASNA_DECODE_BACKEND` chain, which applies when `native` is selected.

- **Decode**: `auto` prefers torchcodec and falls back to native on failure. The `--retarget-high-fps` frame stride is native-only (forcing torchcodec with it errors; `auto` goes native).
- **Encode**: **never selected by `auto`**, because upstream's native encoder outputs 10-bit P010 for HEVC/AV1 and the torchcodec encoder is 8-bit only; selecting it silently would change the output bit depth. It runs only when forced via `--video-encode-backend torchcodec`, for 8-bit sources + HEVC/AV1 + mappable NVENC settings (streaming, `--segments` and fps changes are rejected; frame generation scales its constant frame rate; `--sharpen` gates and `--fmp4` warns). It writes upstream's settings tag into the output's comment like the native encoder. Colorspace is tagged by the encoder's built-in ffmpeg copy-remux with H.273 code points (plus the `hevc_metadata` BSF VUI rewrite for HEVC).
- The startup log shows the chosen backends (`[decode: ..., encode: ...]`), readers and encoders carry a `backend` attribute, and encoding runs on a dedicated worker thread. `jasna/media/backend.py` (selection), `torchcodec_decoder.py`, `torchcodec_encoder.py`.
- **Known gaps**: the torchcodec encoder preserves chapters but drops subtitle and data streams (native preserves all), and its default CQ is hardcoded at 25 instead of upstream's per-codec defaults (an explicit `--cq` does reach it).
- **Status**: verified on both OSes. Design, capability matrix and measurements: [torchcodec_backend.md](torchcodec_backend.md) (decode is neutral; the pipeline is detection-bound).

### 5.2 cuDNN FP8 upsample backend (`--fp8-recon`)

An experimental cuDNN graph-API FP8 backend for the BasicVSR++ **upsample** sub-engine, ported from lada-ex `feat/fp8-recon` (AGPL-3.0). Opt-in via `--fp8-recon` (bridged to `JASNA_FP8_RECON=1` for the GUI and subprocess paths; the GUI has an **FP8 Restoration (experimental)** toggle); default off is unchanged behaviour. Requires an FP8-capable GPU (sm89+), fp16, and the `nvidia-cudnn-frontend` dependency (cuDNN ≥ 9.17 comes with the torch cu130 wheel; Windows adds `triton-windows` for the compiled glue with an eager fallback). Any construction failure logs a warning and falls back to the TensorRT engine.

- When active the TensorRT upsample engine is **not loaded at all** (`load_sub_engines(..., load_upsample=False)`), so its load-time arena is never allocated; the engine file is still built and kept as the fallback. The cuDNN graphs are bucketed up to upstream's fixed `UPSAMPLE_BATCH = 30`, so warmup is independent of `--max-clip-size`, and warmup eagerly builds every T-bucket (jasna clip lengths vary freely).
- Its main use today is the **VRAM budget for co-residence**: `flashvsr-inline` and `swiftvr-inline` auto-enable it so the primary shrinks to ~1.6 GB next to the resident worker. Pipeline-level the VRAM peak drops 0.9–1.7 GB across 480p–4K while e2e fps stays flat (detection-bound); stage output is 64 dB PSNR against FP32, visually indistinguishable from the FP16 engine, and bit-deterministic across runs.
- Integration fix kept here: torch's bundled cuDNN lib dir is put in front of `LD_LIBRARY_PATH` before `import cudnn` (nvvfx prepends a dir holding a bare dispatcher without sub-libraries). The same path leak is why external workers now get a cleaned environment ([7](#7-fixes-kept-on-this-branch)).
- `jasna/restorer/fp8_upsample.py` plus the injection/fallback/close changes in `basicvsrpp_sub_engines.py`; A/B gate benchmark via `jasna --benchmark --benchmark-filter fp8`.
- **Status**: verified on Linux and Windows (A/B benchmark passes every gate on both; full 1080p pipeline runs). Frozen-build packaging of `cudnn` on Windows is unverified (falls back to TRT). Details: [fp8_recon.md](fp8_recon.md).

### 5.3 TensorRT-RTX flavor (`nvidia-rtx` extra)

Installing the `nvidia-rtx` extra instead of `nvidia` switches the whole TensorRT stack (raw-API detection engines and the torch-tensorrt dynamo BasicVSR++ sub-engines) to TensorRT-RTX. The point is first-run latency: TensorRT-RTX compiles JIT, so cold engine builds drop 3–9x (RTX 5080: RF-DETR v6 36 s → 5 s, the six BasicVSR++ sub-engines 55 s → 16 s; RTX 5060 Ti: 118 s → 16 s / 143 s → 52 s). Costs: detection inference is ~12 % slower (pinned by per-layer profiling on TensorRT-RTX's JIT fusion quality around the mask output; not recoverable with CUDA graphs, specialization strategy, AOT builder knobs or newer tensorrt-rtx releases, so the gap is accepted), steady-state throughput on long videos is about −10 %, and the BasicVSR++ engines pay a few seconds of load-time JIT per process (the raw-API engines get a version-tagged `.jitcache` next to the engine, re-persisted after inference so shape-specialized kernels survive restarts). Output agreement with the standard flavor: PSNR 46.7 dB / SSIM 0.994 on the e2e clip.

- Implementation: flavor detection is a `find_spec("tensorrt_rtx")` probe in `engine_paths.trt_flavor()` (immune to torch-tensorrt-rtx's `sys.modules["tensorrt"]` alias; `JASNA_TRT_FLAVOR` overrides); `jasna/trt/_backend.py` is the sole import point for the TRT module (a guard test enforces it); `engine_system_suffix()` injects a `.rtx` tag so both caches coexist in one `model_weights`. TensorRT-RTX builds strongly typed and rejects `BuilderFlag.FP16`, so the ONNX is converted wholesale to fp16 before parsing (`_convert_onnx_bytes_to_fp16`, including RF-DETR's 44 baked-in `Cast(to=float32)` nodes; without it the build silently produces an fp32 engine 5x slower). One venv holds one flavor. Whole-graph CUDA graph capture for the detection engines exists opt-in behind `JASNA_TRT_RUNNER_CUDAGRAPHS`.
- **Status**: verified on Linux and Windows. Details: [tensorrt_rtx.md](tensorrt_rtx.md).

## 6. GUI

### 6.1 A/B model comparison (Segment Editor)

A modal window opened from the Segment Editor compares two detection-model × restoration-checkpoint combinations side by side on the same frame or a short playback window, replacing the "process the whole video twice" workflow for every model upgrade or fine-tune evaluation. Three views: **Restored**, **Detection** (mask overlay + score, per-side confidence slider), **Clip** (synchronized playback; side A is the clock). Runs are explicit via **Run**; selection or time changes only mark a side "(stale)".

- **Sequential by construction**: torch_tensorrt's CUDA-graphs mode is process-global and capture is poisoned by CUDA calls from other threads, so both legs run A→B on one worker thread (`jasna/gui/ab_compare_worker.py`); a request arriving between legs aborts leg B; if both resident sessions OOM, both slots are released and the current leg retries once cold.
- **Pipeline reuse**: both legs run upstream's shared `run_restoration_pass()` (the restore-preview pass over a bounded window collecting PIL images). modi originally extracted this function; upstream v0.11 introduced its own (`b0e5e5c`), which the A/B now uses.
- **Visible execution path**: BasicVSR++ silently falls back to PyTorch when its sub-engines are missing. `BasicvsrppMosaicRestorer.tensorrt_active` drives per-side **TRT** / **PyTorch** badges; a checkpoint without engines runs in PyTorch (`compile_basicvsrpp=False`) instead of entering the 15–60 min compile subprocess, and the in-window **Compile engines** button compiles them explicitly (engines are per checkpoint, so the other side's badge updates too).
- **EMA guard**: `load_model` is hardwired to `is_use_ema=True`, so a checkpoint without `generator_ema.*` keys silently runs with random weights. `jasna/restorer/checkpoint_info.py` detects this before running (mmap load + key scan, cached by path/mtime/size) and refuses.
- **Selectable checkpoint**: the GUI's restoration model path is centralized in `default_restoration_model_path()` (`jasna/engine_paths.py`) and `build_video_session` takes a `restoration_model_path`.
- **Shared zoom/pan**: `jasna/gui/preview_zoom.py` (normalized coordinates, HiDPI division from issue #229) drives both panes through one `ZoomPanController`; the Segment Editor's own math delegates to the same module.
- **SeedVR2 side**: when the external checkout (`$JASNA_SEEDVR2_REPO`, default `~/seedvr2_videoupscaler`) and the LoRA are present, a `seedvr2` entry joins the checkpoint dropdown; the EMA check, TRT badge and compile button are skipped for that side, and VR videos are refused for it with a localized message.
- New UI strings in all five locales. `jasna/gui/ab_compare.py`, `ab_compare_worker.py`, `preview_zoom.py`, `jasna/restorer/checkpoint_info.py`, entry point in `segment_editor.py`.
- **Status**: `tests/test_ab_compare_{worker,window}.py`, `test_preview_zoom.py`, `test_checkpoint_info.py`, the integration part of `test_segment_editor.py` (CPU-only; worker sequencing pinned by tests). Verified on Linux with 720p–8K VR 60 fps material and on Windows 11 (HiDPI 125 %/150 %, Tk-grab modal control, the compile subprocess, queue-start locking). User documentation: [segments.md](segments.md#ab-model-comparison).

### 6.2 Restoration checkpoint selection in the Video Player

The restored-video player's settings card gains a **restoration checkpoint** selector next to detection model, secondary restoration and confidence: the `*.pth` files directly under `model_weights/` (the same `discover_restoration_checkpoints()` as the A/B comparison), default generic v1.2. The selection travels as `AppSettings.restoration_checkpoint` (the checkpoint stem; empty = default) and is part of `video_session_key()`, so switching rebuilds the player pipeline like a detection-model change; `resolve_restoration_checkpoint()` maps stem → path. The guards mirror the A/B comparison: a checkpoint without EMA weights is refused before the session is built, and a checkpoint without compiled sub-engines plays in PyTorch (`compile_basicvsrpp=False`) with the status saying so (to produce the engines, run the CLI with `--restoration-model-path` or use the A/B window). Since the v0.11.1 base `AppSettings.restoration_model` is upstream's model choice (BasicVSR++ / LTX); old modi presets that stored the stem there are migrated on load.

## 7. Fixes kept on this branch

Bugs fixed on `modi` that upstream does not have. Fixes upstream has since made itself are in [Appendix A](#appendix-a-absorbed-by-upstream-or-dropped).

- **Primary-restore buffer-hold race** (`jasna/restorer/restoration_pipeline.py`): a view into the TRT runner's persistent output buffer was held and copied out to uint8 later on another thread, so the next clip's inference could overwrite it first, leaving a restored region with another clip's data. `primary_raw = self.restorer.raw_process(...).clone()` copies out on the primary stream before the buffer is reused. Upstream v0.6.2's decoder stream-sync fixed the other (decoder-side) cause of the Linux "chunk movement" stutter (issue #2 / upstream #158); this restore-side site is independent of it.
- **Frame generation across a folder batch**: the generator is built once and shared across the batch, but `FrameGenerationWriter.close()` used to close that borrowed generator after the first video, so the second video crashed. The writer now leaves the generator alone; whoever built it (the CLI folder loop / the GUI job runner) closes it once after the batch.
- **External workers inherited jasna's library dirs** (`jasna/restorer/worker_env.py`, 2026-10-16): the FlashVSR, SwiftVR and SeedVR2 workers run their own torch and cuDNN but inherited `LD_LIBRARY_PATH`; with FP8 on (which `swiftvr-inline` enables) a worker on a newer torch loaded jasna's cuDNN sub-libraries and died at its first convolution (`CUDNN_STATUS_SUBLIBRARY_LOADING_FAILED`, surfaced when the SwiftVR venv moved to torch 2.14 / cuDNN 9.24). `external_worker_env()` now builds every worker environment: `PYTHONPATH` dropped, and `LD_LIBRARY_PATH` entries inside this interpreter's installation removed.
- **Blank modal dialogs on Linux/X11**: the About dialog and the first-run wizard defer upstream's `grab_modal()` by 250 ms (`jasna/gui/app.py`, `jasna/gui/wizard.py`) so the widgets are painted before the modal grab; under some X11 window managers an early `grab_set()` left the non-resizable `CTkToplevel` blank. Upstream's other dialogs call `wait_visibility()` before the grab and are unchanged.
- **cuDNN load order for the FP8 backend**: see [5.2](#52-cudnn-fp8-upsample-backend---fp8-recon).
- **YOLO ONNX export on CPU for frozen builds**: ultralytics' GPU export initializes torch CUDA before TensorRT and breaks the init order in a frozen binary (CUDA error 100), so the detection ONNX is exported on CPU (`half=False, device="cpu"`); upstream's save/restore of `CUDA_VISIBLE_DEVICES` is kept. The engine is still built fp16.
