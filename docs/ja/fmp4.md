# `--fmp4`: 処理中に再生できる MP4 出力

`--fmp4` は、ファイル出力の処理を走らせたまま結果を確認するためのオプションである。
有効にすると `.mp4` / `.mov` の出力ファイルが **fragmented MP4**（fMP4）で書き出され、処理の途中でもプレイヤーで開いて再生できる。
処理を中断しても、ファイルはその時点まで再生可能な状態で残る。
既定は off で、その場合の挙動は従来と完全に同じである。

v0.7.x までは処理中に生の .hevc ストリームが出力フォルダへ書かれ、それを開けば途中経過を確認できた。
v0.8.0 でメディア層が PyAV 化されて最終ファイルへ直接書く方式になり、この確認手段が失われた。
本オプションはその置き換えである。

## 使い方

```bash
jasna --input in.mp4 --output out.mp4 --fmp4
```

処理中の出力ファイルを mpv などのプレイヤーで開けば、そこまでの結果を音声込みで確認できる。

GUI では、エンコード設定の「フラグメント化 MP4」トグルが同じ機能に対応する。
CLI と GUI で動作に違いはない。

## 仕組み

### 通常の MP4 が途中再生できない理由

MP4 の再生には **moov アトム**（コーデック初期化情報と、全サンプルの時刻・ファイル内オフセットの索引）が必須である。
通常の書き出しでは、muxer はこの索引をメモリに温め、コンテナの close 時に一度だけ書く。
したがって書き込み途中のファイルは索引を持たず、プレイヤーは解釈できない。

jasna の既定はさらに `movflags +faststart` を指定しており、close 時に moov をファイル先頭へ移す第 2 パスが走る。
これは完成後のプログレッシブ再生（ダウンロードしながらの再生）を速くする指定であって、書き込み途中の再生は依然として不可能である。

### fragmented MP4

`--fmp4` 有効時は、movflags を `+frag_keyframe+empty_moov` に切り替える。

- **empty_moov**：サンプル情報を持たない moov をファイル先頭に即時書き込む。プレイヤーは開いた瞬間にコーデック初期化情報を得られる。
- **frag_keyframe**：メディアデータを「巨大な mdat + 終端の索引」ではなく、キーフレームごとの moof + mdat 断片として逐次書き出す。各 moof が自分の mdat 内のサンプル表を内包するため、断片が 1 つ完成するたびに再生可能範囲が伸びる。

断片の粒度はキーフレーム間隔で決まり、NVENC 既定（`g=250`）では 30 fps で約 8 秒ごとになる。
`+faststart` は fragmented 出力では mov muxer に無視されるため付けない。
`+default_base_moof` はブラウザの Media Source Extensions 向けの指定であり、ローカルプレイヤーでの再生には不要なので付けない。

jasna のネイティブエンコーダは音声を映像とインターリーブしながらライブで mux しているため、途中再生には音声も含まれる。

副次的な利点として、close 時の moov 再配置パスが不要になるぶん終了が速く、処理がクラッシュ・中断してもその時点までの断片が再生可能なファイルとして残る。

## 対象外の組み合わせ

いずれの場合もエラーにはせず、警告を出して通常の MP4 出力で処理を続ける。

| 条件 | ファイル出力 |
|---|---|
| `--stream` 併用 | 無視（警告）。ファイルを保存しないモードのため意味がない |
| `--segments`（スマートレンダー） | 通常 MP4 に退避（警告） |
| `--secondary-restoration flashvsr` | 非対応（警告） |
| `--encode-backend torchcodec` | fMP4 にならない（警告） |
| フォルダ一括入力 | 制限なし。ファイルごとに fMP4 |
| `.mkv` など mp4/mov 以外の出力 | movflags 対象外（元々途中再生可能） |

`--segments` は出力を処理完了後に組み立てるため、途中再生の対象になるファイルが存在しない。
torchcodec エンコードバックエンドは一時ファイルへ書いて最後に remux する方式のため、途中再生の利益がない。

## 制約

- fMP4 の先頭 moov は総時間を持たないため、書き込み中のファイルを開くと総時間表示とシークが不正確になることがある。
- fMP4 に対応しないごく古いプレイヤーでは再生できない。
- 処理速度への影響は計測可能な範囲では生じない（実測でベースラインと同等）。
- `--frame-gen` / `--retarget-high-fps` とは併用できる。
- 処理中の中断（Ctrl+C）はプロセスが即座には終了しない（ワーカースレッドの join 中に割り込みが入るため。フラグの有無によらない既存挙動）。出力ファイルはその時点まで再生可能な状態でディスクに残る。

## 実装とテスト

主要な変更点は次のとおり。

- `jasna/media/video_encoder.py`：movflags の決定を純関数 `_mov_container_options()` に切り出し、`NvidiaVideoEncoder` に `fmp4` パラメータを追加。
- `jasna/media/backend.py`：`make_video_encoder()` の引き回しと torchcodec 選択時の警告。
- `jasna/pipeline.py`：非 mp4 出力・`--segments` のフォールバック判定とエンコーダへの引き渡し。
- `jasna/main.py`：フラグ定義と、`--stream` / `--segments` / flashvsr 併用時の警告。
- GUI（`jasna/gui/`）：`AppSettings.fmp4`、エンコード設定のトグル、5 言語のロケール。

テストは `test_video_encoder_unit.py`（`_mov_container_options` の単体）、`test_video_backend_fallback.py`（バックエンド分岐）、`test_pipeline_run.py`（フォールバック）、`test_main_validation.py`（CLI 結線）、`test_locales.py`、`test_preset_migration.py` に追加した。
CUDA を要するもの（`test_video_encoder_mux.py` の fMP4 レイアウト検査、切り詰めファイルの途中再生検査、音声 mux 検査）はコードのみ追加済みである。

## 検証状況

CPU テストと CUDA テストはいずれも通過している（フルスイート 1754 passed / 21 skipped）。
残る 9 件の失敗は `jasna.protection` 欠落と GUI レイアウトに起因する既存のものであり、変更前の HEAD でも同一に失敗することを worktree で確認済みである。

実機検証は RTX 5080（Linux、1920x1080・29.97 fps・140 秒・4203 フレーム・音声 AAC のクリップ）で次を確認した。

**コンテナ構造**：フラグ有りの出力はトップレベルが `ftyp / moov / moof+mdat ×17 / mfra` で、moov が先頭に来て断片が続く。既定の出力は `ftyp / moov / free / mdat` で mdat が 1 個だけである。

**途中再生**：処理中（61% 時点）に出力ファイルをコピーして検査したところ、フラグ有りは 2250 フレーム + 音声 AAC がデコードでき、既定の同条件のコピーは `moov atom not found` で読めなかった。fMP4 の効果と、途中再生に音声が含まれることを実測で確認したことになる。

**フォールバック**：`--stream` 併用は警告（`--fmp4 is ignored with --stream`）を出してストリーミングとして動作を継続する（引数エラーで終了しない）。`--segments` は警告後に通常 MP4（moof 0）を生成。`.mkv` 出力は matroska として正常に生成される。フォルダ入力は警告なしで各出力ファイルが fMP4（moof 17）になった。

**性能**：フラグの有無で計測可能な差はない。交互に 3 回ずつ実行してベースライン 141.1 / 141.3 / 142.3 fps、フラグ有り 141.8 / 140.0 / 140.8 fps。両者のばらつきは実行ごとのノイズの範囲に収まる。

**出力の同等性**：ベースラインとフラグ有りのいずれも 4203 フレーム、音声 AAC で一致した（fMP4 はコンテナが申告する総時間のみ 140.37 秒と 0.11 秒長く出るが、デコードされるフレーム数は同一である）。

`--encode-backend torchcodec` のフォールバックは、依存パッケージが手元にないため単体テストによる検証のみである。
